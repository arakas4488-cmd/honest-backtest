Track record

Confirmed Findings

Four bugs I found by reading open-source trading-bot code, reported publicly, and that the maintainers confirmed and fixed. Every item links to the original report and to the fix, so you can check it yourself instead of taking my word for it.

I review trading-bot code for one class of problem: code that behaves differently than its README or its backtest claims it does. The method is the same each time. I read the code, open a public issue describing what I found and why it matters, and leave the fix to the maintainer. I do not exploit anything.

Not every report gets a reply. These four did. Dates are taken from the linked GitHub pages.

Missing slippage clamp

1. A slippage guard that stopped guarding at 100%

Project: 0xfnzero/sol-trade-sdk

The Bonk/LetsBonk slippage helpers did not apply the maximum-slippage clamp that the PumpFun path already used. At 100% slippage the minimum accepted output became zero, which means no price protection at all, and one helper could divide by zero.

Report: issue #111 (Aug 5, 2026)  ·  Fix: PR #112, merged (Aug 6, 2026)

Stale price in the exit path

2. A stop-loss that priced its own exit off the entry price

Project: chainstacklabs/pumpfun-bonkfun-bot

The exit sell passed the position's entry price into the seller, and that value is the slippage floor. An exit fires precisely when the price has moved away from entry, so the floor was priced off the wrong number. Separately, position monitoring could stop silently after a failed sell.

Report: issue #189 (Aug 5, 2026)  ·  Fix: PR #193, merged (Aug 24, 2026)

Wrong aggregation

3. A dashboard that added returns instead of compounding them

Project: thanhphan20/freq-trading-bot

The dashboard aggregator summed each trade's profit percentage instead of compounding it, so total return diverged from reality as trades accumulated. The Sharpe ratio was computed on raw dollar P&L rather than on a return series.

Report: issue #7 (Aug 4, 2026)  ·  Fix: PR #9, merged (Sep 16, 2026)

A crash that removes the safety net

4. An exception that could take the stop-loss down with it

Project: titouannwtt/freqtrade-ultimate

One strategy retried a data fetch twice, but the third attempt sat outside any error handling, so a routine failure of the unofficial data source interrupted the whole bot cycle. The strategy's stop-loss only exists while the process is running, so a crash with a position open leaves that position unprotected.

Report: issue #38 (Aug 3, 2026)  ·  Fix: commit 38c3777 (Aug 25, 2026)

What I did and did not do

  • I found each of these by static reading of the source. The fixes were written and merged by the maintainers, not by me.
  • The issue text, the fix, and the merge date are on GitHub for each item; none of this relies on private correspondence.
  • I describe what the code did at the time of the report. I am not making claims about money lost or gained by anyone's live trading.
